## Вердикт

ТЗ в целом верное: Bridge v2 нельзя выбрасывать, публичный Issue не командный канал, GitHub-текст не полномочие, `workspace.write` вместе с `workspace.exec` уже равны запуску нового user-level кода, криптографию имитировать нельзя, admin-shell модели давать нельзя.

Задание нельзя выполнять дословно как один объём. Внутри ТЗ есть противоречия между фазами, протоколом, полномочиями и критерием готовности. Ниже для каждого выбрано fail-closed решение. Это не вопросы к пользователю.

Два blocking bug из пунктов 9–10 на текущем `main` реальны. Кроме них есть дефект, который ТЗ не называет: проверка collaborators и deploy keys читает одну страницу API и поэтому не доказывает отсутствие лишнего writer.

## Что сверено с кодом

Прочитаны `bridge-v2/mailbox.ps1`, `arena-mailbox-put.ps1`, `arena-common.ps1` (`Reserve-TaskSeq`, `Resolve-ExpiredReservations`), цикл `arena-bridge-v2.ps1`, `actions.ps1`, repo guard. В этой среде нет `dotnet`.

Текущий Bridge действительно сохраняет полезное и это нельзя сносить:

- action id вместо shell-строки, четыре read-only действия;
- нет `Invoke-Expression` и нет `powershell -Command` с внешним текстом в шести скриптах исполнителя;
- durable inbox, atomic write, state до и после выполнения;
- replay по `task_id` и `seq <= last_seq`;
- crash во время `RUNNING` не перезапускается;
- публикация по маркеру, id комментария строкой, повторный POST не создаётся;
- repo guard перед действием;
- mailbox выключен без локального `mailbox.json`;
- разрешение mailbox — private, не форк, точное имя, владелец, нет лишнего push/admin/maintain, нет deploy key;
- публичный `GIT_STATUS` — сводка, `GIT_DIFF` не публикуется.

Этого недостаточно для Local Agent. Пункт 0 ТЗ переоценивает текущий read-back: результат — это вывод процесса, а не повторное чтение фактического состояния. Для `git status` это приемлемо. Для будущей записи файла или стены в Archicad — нет.

## Подтверждённые баги

### BUG 1. Starvation после старых remote-файлов. Подтверждён

`Invoke-MailboxSync` сортирует имена и обрывает цикл на 20 обработанных файлах (`mailbox.ps1`, проверка `$handled -ge 20`). Уже terminal/seen файл всё равно увеличивает счётчик: его снова скачивают, `Import-MailboxEnvelope` выходит, но слот окна потрачен.

Следствие: 20 старых `inbox/1.json` … `inbox/20.json` навсегда закрывают `inbox/21.json`. Увеличение лимита до 100 или 1000 тот же класс ошибки.

Вторая граница, которую ТЗ не называет: `gh api repos/.../contents/inbox` вызывается один раз, без `page` и без разбора `Link`. GitHub для каталога отдаёт не больше 1000 имён. Обрезка незаметна. Курсор по «первой странице списка» эту дыру не закрывает.

Fail-closed для будущего исправления, без включения live mailbox и без новых действий:

- окно «первые N» не является очередью;
- уже обработанный remote id не занимает слот поиска новой задачи;
- список, который выглядит усечённым, не считается полным;
- обработанные файлы должны уходить из polled-набора (archive или отдельный index), а не копиться в `inbox/`;
- archive — служебная запись control plane, не команда. Исполнять `archive/` нельзя. Имя файла только по allowlist, поле `path` из API по-прежнему игнорировать;
- удаление или перенос не должен становиться произвольной записью в репозиторий.

Обязательный тест из ТЗ верный: больше 25 remote-файлов, первые больше 20 уже terminal, новая задача находится и выполняется один раз, restart результат не меняет. К нему нужен ещё тест усечённого списка: неполная страница не маскируется под «новых задач нет».

### BUG 2. Столкновение staging и local exec seq. Подтверждён. Механизм точнее, чем в ТЗ

`arena-mailbox-put.ps1` берёт номер через `Reserve-TaskSeq`, пишет `mailbox-staging/<seq>.json`, сразу удаляет reservation и не удаляет staging ни после успешного push, ни после ошибки push.

`Reserve-TaskSeq` считает staging занятым номером навсегда. `Resolve-ExpiredReservations` смотрит только `reservations/`, не staging. Lease staging не истекает.

Воспроизводимая клинья:

1. `last_seq = N`.
2. Producer резервирует `N+1`, пишет `staging/N+1.json`, удаляет reservation, пушит remote `inbox/N+1.json`.
3. Import вызывает тот же allocator, видит staging и создаёт local inbox `N+2`.
4. Цикл Bridge ждёт inbox `N+1`, видит `N+2`, пишет `GAP` и останавливается.
5. `inbox/N+1.json` не появится никогда: staging не является inbox-задачей.

Та же клинья без GitHub. Dry-run или упавший push оставляет staging. Следующий router резервирует `N+2` и кладёт его в inbox. Bridge снова ждёт `N+1`.

Поэтому формулировка «remote side никогда не выбирает exec_seq» верная, но недостаточная. Сейчас remote filename всё ещё выбирается тем же allocator, а staging навсегда занимает дыру, которую local gap-wait считает незакрытой. Smoke `[5]` и `[6]` этот gap-wait требуют для локальной очереди без reservation. Его нельзя отменять. Убрать надо чужие tombstone из этого числового пространства.

Fail-closed:

- remote id и local exec seq — разные пространства уже в исправлении этого бага, не «когда-нибудь в C#»;
- staging не называется `<exec_seq>.json` и не участвует в расчёте следующей локальной дыры;
- успешный или неуспешный push не оставляет вечный staging в пространстве исполнения;
- local gap-wait остаётся только для реального отсутствующего inbox-файла, а не для служебного staging;
- тест: producer доводит задачу до fake remote, import исполняет её, local seq не равен remote id, второй producer одновременно не клинит очередь, restart не исполняет повторно.

Полный конверт с `request_id` / `job_id` / `step_id` — контракт фазы 1. Нельзя чинить клинью большим переписыванием протокола в том же коммите, где только убирается starvation. И нельзя оставлять клинью до появления C# agent.

## Дефект, который ТЗ пропустило

### Неполная проверка прав. Fail-open

`Test-MailboxPermission` правильная по смыслу, но список collaborators и deploy keys читается одним вызовом без пагинации. У GitHub страница collaborators по умолчанию 30. Writer или ключ на следующей странице не виден, и опрос может разрешить read-only задачу.

Это не повод разрешать `workspace.write` на текущей модели. Это повод не называть текущую проверку полным доказательством даже для четырёх read-only действий.

Fail-closed, когда этот код снова будут трогать: неполная страница — это `collaborators-unreadable` или `keys-unreadable`, задача не исполняется. Либо страницы читаются до конца и любая ошибка продолжения тоже отказ. Сейчас live mailbox выключен, поэтому дефект латентный. Включать mailbox до закрытия этой дыры нельзя.

Отдельное уже задокументированное ограничение остаётся: скомпрометированный аккаунт владельца всё ещё может поставить четыре read-only действия. Это не лечится пагинацией и не должно прикрываться фальшивой подписью.

## Что ТЗ правильно запрещает

Эти запреты принимаются без смягчения:

- публичный Issue не источник команд;
- JSON, README, логи, OCR, UI-текст, вывод локальной модели и текст Archicad — данные, не инструкции;
- строка `ignore previous instructions` ничего не разрешает;
- удалённая сторона не передаёт shell-строку и не передаёт корень файловой системы;
- `workspace.write` плюс `workspace.exec` — это запуск нового кода пользователя, action id сам по себе это не сдерживает;
- repo-permission model не авторизует write, exec, Archicad write, UI, установку пакетов и admin;
- модель не получает admin shell;
- elevated helper не строится в текущих фазах; будущая граница — узкий typed allowlist, не `RUN_AS_ADMIN` с произвольной командой;
- не автоматизировать UAC и Secure Desktop;
- не автоматизировать Teamwork/BIMcloud и не отдавать модели JWT или refresh token;
- зелёный тест не доказательство корректности и не повод ослаблять тесты незаметно;
- первый зелёный прогон недостаточен;
- child process не наследует GitHub token, API keys и authorization secrets;
- agent не правит сам себя через workspace job: install, policy, profiles, updater и helper лежат вне writable workspace.

## Противоречия и выбранные решения

Мелочи не спрашиваются. Где ТЗ оставляет «или», выбран отказ.

### 1. Фазы против критерия «сделать всё»

Пункты 86–88 ограничивают работу тремя фазами и запрещают Archicad mutation, GUI, screenshot transport, пакеты, admin helper, live powerful execution, self-update, Windows Service и installer. Пункты 56–75 и критерий готовности читаются так, будто это тоже надо построить.

Решение: 56–75 — ограничения будущего дизайна, не код этой ветки. В handshake нельзя объявлять несуществующие capabilities. `ui.control`, `archicad.write`, `system.admin`, `package.user_install` в реализации фаз 0–2 отсутствуют, а не «выключены флагом».

### 2. Локальная модель «выбирает action» против «не переосмысливает команду»

Пункт 4 разрешает локальной модели выбрать простой action. Пункты 3 и 96 запрещают ей решать и переинтерпретировать команду. Пункт 42 считает её вывод недоверенным.

Решение: вывод локальной модели никогда не становится action. Профили FAST/AGENT/DEEP — сменяемая конфигурация advisory-вызова. Agent обязан работать без локальной LLM. В вертикальном срезе достаточно интерфейса и fake provider. Endpoint только loopback, timeout обязателен, ответ — данные.

### 3. `FILE_APPLY_PATCH` в фазе 2 против запрета powerful remote execution

Пункт 13 запрещает авторизовать write текущей repo-permission моделью. Пункт 86 включает patch в вертикальный срез. Пункт 88 запрещает исполнение произвольного кода из облака.

Решение: patch в срезе доступен только тестовому драйверу внутри процесса, на временном workspace, который не является репозиторием проекта и не является каталогом agent/policy. Путь из GitHub, Issue, mailbox и локальной модели до `workspace.write` не доходит. Единственная удалённая политика — deny. Интерфейс `IAuthorizer` существует, но не изображает криптографию: реализация для remote — отказ, для test harness — явное локальное разрешение теста.

Реальный проект `arena-archicad-project` в этом срезе не регистрируется как writable workspace.

### 4. Два хранилища состояния

PowerShell bridge держит `state.json`. Новый agent по ТЗ должен держать SQLite. Общая запись в оба создаст два источника правды и два исполнителя одной очереди.

Решение: bridge не переводится на SQLite в этих фазах. C# agent не читает и не пишет `state.json` bridge и не опрашивает mailbox. Миграция очереди — отдельное решение после аудита, не побочный эффект вертикального среза.

### 5. Ночной цикл и commit/push против отсутствия контроллера

Пункты 6, 48 и 71 описывают ночной цикл с commit/push. Пункты 7, 50 и 88 запрещают работу прямо в `main`, merge без отдельного разрешения и live powerful execution. Постоянного cloud controller ещё нет. Chat session не является им.

Решение: вертикальный срез не коммитит и не пушит репозиторий пользователя, не ставит startup task, не запрещает sleep и не запускает фоновый poller решений облака. Commit внутри временного git-репозитория теста допустим только без credentials и без сети.

### 6. Сеть

Пункт 30 требует network disabled для непроверенного кода. Самому agent для будущего control plane сеть нужна, модели — только localhost.

Решение: дочерний профиль по умолчанию без сети, без наследования окружения. Ограничение Windows host execution честно описывается: полный запрет сети процессу на Windows не обещается, если механизм не реализован. Не писать в документе, что sandbox уже есть.

### 7. Unknown fields

Пункт 78 разрешает либо fail-closed, либо задокументированную совместимость.

Решение: входящие security-sensitive конверты с неизвестным полем отвергаются. Совместимость вперёд допустима только у результатов, которые agent сам отдаёт.

### 8. Какой id идемпотентен

В новом конверте три UUID, но не сказано, какой запрещает повторное исполнение.

Решение: `step_id` — ключ идемпотентности исполнения. Повтор того же `step_id` возвращает сохранённый результат и не исполняется. Новый `step_id` — новый шаг, даже если действие похоже. `request_id` — транспортный id. `job_id` группирует шаги и не заменяет idempotency key.

### 9. `depends_on`

Не описаны циклы и вечное ожидание. Это тот же класс, что permanent GAP.

Решение: цикл, отсутствующая зависимость и зависимость дольше `expires_at` или deadline job — терминальный `REJECTED` или `NEEDS_REVIEW`, без исполнения и без вечного ожидания. Бесконечный retry запрещён отдельно бюджетом job.

### 10. Hash при записи

Пункт 23 требует `expected_sha256` при изменении, но не различает create и update.

Решение: существующий файл без ожидаемого hash не перезаписывается (`CONFLICT`). Create только если путь отсутствует в момент exclusive create. Несовпадение hash — `CONFLICT`, не overwrite. После replace — read-back и сравнение hash. Падение после durable `RUNNING`: если файл уже совпал с запрошенным hash, повторная запись не делается; если не совпал, повтор вслепую не делается, состояние `FAILED` или `NEEDS_REVIEW`.

### 11. Срок конверта и ночная задача

Текущий mailbox отвергает конверт длиннее 24 часов. Ночная задача из пункта 46 может быть длиннее одного конверта.

Решение: не растягивать текущий mailbox до бесконечности. У шага свой `expires_at`. У job свой deadline. Истёкший шаг не исполняется. Job deadline не продлевается молча.

### 12. Публичные результаты

Пункт 12 оставляет публичный Issue только для уже очищенной read-only информации. Текущий код всё ещё публикует version, сводку status и урезанный log. Для четырёх старых действий это уже принятая политика. Для нового agent это слишком широко: путь, hash файла и тело патча в Issue не попадают.

Решение: новые результаты agent локальные, пока нет отдельного приватного control plane. Старую публикацию четырёх действий в этом задании не расширять. Source repo, control repo и artifact storage не смешивать. Артефакты не коммитятся в source repo.

### 13. Secret scan из пункта 84

Буквальный поиск слов `password=`, `token=`, `secret=`, `Authorization:` сломается на собственном sanitizer и на отрицательных тестах. Это не повод вырезать sanitizer.

Решение: сканировать diff на живые секреты и token-shaped строки. Упоминание denylist в коде защиты — не секрет. Настоящий `ghp_` / `github_pat_` / ключ в diff — отказ от коммита.

### 14. C# и эта среда

Пункт 16 выбирает C# / .NET для agent core. PowerShell остаётся compatibility layer. Это принимается. В текущей среде нет `dotnet`, поэтому вертикальный срез нельзя честно назвать проверенным, пока SDK не установлен и тесты не прогнаны дважды. Ставить SDK и писать agent в обход этого аудита нельзя: пункт 76 требует сначала аудит.

PowerShell 5.1 остаётся ограничением для существующих bridge-тестов. Новый C# код не заменяет этот контракт, пока bridge ещё исполняет четыре действия.

### 15. Политика веток

Пункты 7, 89 и 91 для этой работы отменяют прежний порядок «push в `main` и одна Windows-проверка». Новая работа — только `arena/local-agent-v0` или другое имя feature branch. `main` не сливается без отдельного разрешения после независимого аудита. Пользователю не даётся `git pull` и не даётся Windows-тест как следующий шаг. Следующий внешний шаг после реализации — независимый аудит, не включение live.

Этот аудит сам ничего не пушит.

### 16. Один launcher против набора процессов

Пункт 2 хочет один запуск. Пункты 54 и 67 описывают Session Companion и Elevated Helper как отдельные процессы. Пункт 88 запрещает их реализацию сейчас.

Решение: фаза 2 — один процесс без listener, без named pipe, без UI. Описание ACL для будущего helper остаётся документом. Слушающий сокет «на будущее» не создаётся: это новая поверхность атаки.

### 17. Execution profile

Профиль — политика, не данные workspace. Job не может изменить профиль, которым потом запустит свой код. В фазе 2 профиль теста зашит в agent или лежит вне writable workspace и сверяется по hash. Произвольный argv из задачи отвергается.

### 18. Process stop

PID недостаточен. Нужны executable identity и start time. Убивать можно только процесс, который agent сам запустил и записал. Совпадение имени с процессом пользователя не даёт права на kill. Timeout обязан ограничивать дерево детей, которых agent создал. Чужой Archicad, браузер и shell не входят в kill-list этой фазы, потому что agent их не запускает.

Stdout читается с байтовым пределом во время чтения. Достижение предела убивает управляемого ребёнка. Нельзя сначала собрать неограниченный вывод в память.

### 19. Файловая канонизация

Текущий repo guard проверяет reparse point только у самого workdir и сравнивает `rev-parse --show-toplevel`. Это не защита от `..`, junction на родителе, UNC, device path и ADS для будущих file API. Пункт 20 для нового agent обязателен. Нельзя писать в архитектуре, что текущий guard уже закрывает эти классы.

### 20. Atomic write сегодня

`Write-FileAtomic` делает temp и replace, но не fsync и не read-back hash. Для bridge это известный предел. Для `FILE_WRITE_ATOMIC` в срезе flush и проверка hash обязательны. Кодировка, BOM и LF/CRLF входят в hash, а не нормализуются молча.

## Остаточный риск, который фазы 0–2 не снимают

- Владелец mailbox может поставить четыре read-only действия, если канал когда-нибудь включат.
- Локальный inbox Bridge по-прежнему может писать любой локальный процесс. Это M-8. Новый agent не должен унаследовать открытый inbox как доверенный.
- Публичный Issue всё ещё получает очищенные version/status/log старого bridge.
- Host execution на Windows не становится sandbox только из-за интерфейса `ExecutionBackend`.
- Зелёные тесты вертикального среза не доказывают безопасность write+exec, потому что этот срез не должен этот путь открывать.
- Нет постоянного cloud controller, значит ночной сценарий из пункта 2 после фаз 0–2 всё ещё не существует.

## Уточнения перед реализацией

Дата: 2026-09-23. Аудит выше принят. Реализация заказана только после записи этих пяти уточнений и аудита составленного ТЗ. Они обязательны. Они не смягчают fail-closed решения аудита.

Ветка реализации: `arena/local-agent-v0`, от `df4427bb087c08fe19c2d23d50a6cfc588f621d5`. `main` этой работой не меняется. Живой mailbox не включается.

### U-1. Пагинация не доказывает единственного writer

Чтение collaborators и deploy keys обязано идти по страницам и обязано отказывать, если страница не прочитана, список оборван или 20 полных страниц не показали конец. Это закрывает дыру «writer на второй странице».

Это не доказательство exclusive writer. Collaborators и deploy keys не перечисляют всех, кто может записать файл. Остаточные пути, которые эта проверка не видит:

- GitHub App и installation token с `Contents: write`;
- учётные данные Actions и `GITHUB_TOKEN` workflow;
- fine-grained PAT и другие интеграции, которые не сидят в этих двух списках.

Этот остаточный риск приемлем только для текущих четырёх read-only действий. Та же модель доверия запрещена для будущих `workspace.write`, `workspace.exec`, `archicad.write`, `ui.control`, установки пакетов и admin. Полный список страниц нельзя описывать как «других writer нет».

### U-2. Текущие права не доказывают происхождение уже лежащего файла

Проверка репозитория отвечает на вопрос «кто может писать сейчас». Она не отвечает на вопрос «кто положил этот файл». Бывший writer мог оставить задачу в `inbox/` и потом быть удалён. Поздняя проверка «сейчас только владелец» всё равно увидит этот файл и не является разрешением на него.

Текущее состояние репозитория — не авторизация конкретной задачи. Это нельзя чинить фальшивой подписью, HMAC «для вида» или метаданными автора коммита. Будущая сильная авторизация должна привязывать конкретную задачу или контроллер: отдельная identity или attestation. Пока этого нет, мощное live-исполнение остаётся выключенным.

### U-3. Удаление remote только после устойчивого локального принятия

Нельзя удалять и нельзя архивировать remote-задачу до устойчивого локального принятия. Порядок:

1. validate / authorize;
2. устойчивая запись disposition по `task_id`;
3. выделение локального слота исполнения;
4. устойчивая локальная запись inbox/задачи;
5. только потом best-effort удаление remote.

Для отказа устойчивая запись rejected достаточна: локальный слот не выделяется, и только после неё можно пытаться удалить remote. Для принятой задачи удаление разрешено только после записи локального inbox. Повторно появившаяся задача не создаёт второе локальное исполнение.

`archive/` не опрашивается и не исполняется. Это не очередь.

Нужны crash-тесты, и каждый этап перезапускается:

- до устойчивого принятия;
- после принятия и до локальной записи;
- после локальной записи и до remote cleanup;
- после remote cleanup.

Логическое исполнение ровно одно. Крючок сбоя — локальная переменная `ARENA_MAILBOX_FAULT` (`before-accept`, `after-accept`, `after-write`, `after-cleanup`), не поле задачи. Поле задачи с таким именем — неизвестное поле, отказ.

### U-4. C# срез не готов, пока он не собран

Вертикальный срез на C# нельзя называть готовым, пока он реально не прошёл `restore` / `build` / `test` на подходящем .NET SDK. Если в этой среде SDK можно поставить, его ставят и продолжают. Если нельзя, большой непротестированный C# не пишется и Phase 2 не объявляется готовой. Тогда заканчиваются проверяемые Phase 0 и контракты, blocker записывается точно, и работа останавливается.

### U-5. Ветка, порядок и live

Только feature branch. `main` не меняется и не сливается этой работой. Phase 0 заканчивается до архитектуры и до agent. Живой mailbox не включается, `mailbox.json` в git не появляется. В конце пользователю не даётся `git pull` и не даётся команда что-либо запускать. Следующий внешний шаг после коммитов — независимый аудит diff, не включение live.

## Аудит составленного ТЗ

Проверен файл `bridge-v2/LOCAL_AGENT.md` до правок Phase 0. Это аудит задания, не отчёт о зелёных тестах.

Сверенные решения, которые ТЗ больше не оставляет открытыми:

- remote id и local exec seq — разные пространства уже в Phase 0. Имя remote — `inbox/<task_id>.json`. Staging — `mailbox-staging/<task_id>.json`. Producer не занимает exec seq.
- `seq` внутри конверта producer — заполнитель схемы, не слот исполнения и не разрешение. Для старых числовых имён несовпадение `seq` и имени по-прежнему отказ.
- Окно 20 — бюджет новой работы, не очередь. Уже терминальный remote-файл с тем же sha не занимает слот и не скачивается снова. Индекс — `filename → sha → disposition` в `state.json`.
- Список contents на 1000 имён неполный. Это не доказательство пустого inbox и не доказательство, что непросмотренного файла нет. Contents API этим ТЗ не «чинится» пагинацией: у каталога GitHub нет следующей страницы после потолка. Остаточный риск записан, а не спрятан.
- Нет sha в списке — файл не считается уже обработанным. Повторное чтение предпочтительнее ложного пропуска.
- `DELETE` best-effort, только allowlist `inbox/<name>`, sha только из listing, не из JSON задачи. Ошибка удаления не откатывает принятие и не повторяет исполнение. `archive/` не запрашивается.
- Held не удаляется: это ещё не локальный inbox исполнения, а текущий approve-путь перечитывает remote. Текущие четыре действия не critical.
- Пагинация collaborators/keys обязательна и fail-closed. ТЗ запрещает называть её exclusive writer и запрещает переносить её на write/exec/Archicad/UI/пакеты/admin.
- Происхождение уже лежащего файла не считается доказанным. Подпись не имитируется.
- Идемпотентность mailbox в Phase 0 — `task_id`. `step_id` — ключ будущего agent, в Phase 0 не подменяется и не объявляется реализованным.
- Новые действия, live mailbox, IPC, GUI, admin helper, Archicad mutation и публикация результатов agent в Issue не входят в Phase 0.
- Локальный gap-wait и smoke `[13]` не отменяются.

Противоречий, которые требовали бы нового вопроса пользователю, нет. Оставшийся риск записан как риск, не как закрытая дыра.
