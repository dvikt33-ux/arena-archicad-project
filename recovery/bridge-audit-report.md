# Независимый аудит Arena Local Bridge

**Объект:** `dvikt33-ux/arena-archicad-project`, папка `bridge-audit`
(ревизия из `main` на 2026-09-22: скачана тарболлом, т.к. прямые
`api.github.com/repos/...` из песочницы отдают 404 — ограничение сети,
обход через `codeload.github.com` сработал).

**Файлы:** `arena-bridge.ps1` (224 строки), `arena-qwen-router.ps1` (126 строк),
ТЗ — `AUDIT.md` (12 разделов, покрытие — в конце отчёта).

**Метод:** построчное чтение обоих скриптов + проверка внешних фактов
(мануал `gh api` — прочитан, флаг `--silent` существует; семантика
PowerShell `-in`/`Trim()`/`Set-Content`/кодов выхода — по документации).
Код НЕ менялся. Эксплойты НЕ запускались на живой машине — все «подтверждённые
баги» подтверждены чтением кода + детерминированными repro, которые можно
повторить на машине пользователя.

**Главный вывод одной строкой:** инъекции через Qwen **нет** (доказано
устройством allowlist), но базовый инвариант «команда не выполняется дважды»
**нарушен тремя независимыми механизмами** (C-1, C-2, H-1), а доставка
результата **молча теряет данные** (H-2). Это и есть Critical/High ядра отчёта.

---

## 0. Уточнение вердикта (v1.1 — после сверки с владельцем)

1. **C-1 / C-2 — архитектурно Critical, по текущему ущербу High.** Пока allowlist
   read-only (`status / log / diff / --version`), повторное выполнение не разрушает
   данные — реальный ущерб ограничен лишней работой и спамом в Issue. Но как только
   в allowlist появится любое пишущее действие (запись файлов, тесты с побочными
   эффектами, `git commit`, операции с Arena/Archicad) — оба механизма немедленно
   становятся Critical по ущербу. Поэтому чинить их нужно в P0, ДО появления таких
   действий (именно это и заложено в Bridge v2).
2. **Поправка к C-1: обычное падение GitHub НЕ вызывает повторного выполнения.**
   Порядок в коде (allowed-ветка): выполнить → записать result → **записать state** →
   обновить `$lastTaskId` → затем `Send-ToGitHub`. `Send-ToGitHub` поглощает отказ
   API через `$LASTEXITCODE` (3 ретрая → `return $false`), исключений не бросает.
   Значит «GitHub недоступен» = задача помечена завершённой, а результат **теряется
   без гарантированной досылки** — это H-2 (нужен outbox), а не C-1. Re-exec в C-1
   требует именно **брошенного исключения** внутри try: `gh` отсутствует в PATH
   (`CommandNotFoundException` — `Send-ToGitHub` его не ловит), `Push-Location`
   не удался (нет папки проекта), запись result-файла не удалась. Эти случаи
   подтверждены кодом и остаются в силе.
3. **H-2 — теперь главная реальная проблема доставки v1**; именно под неё в v2
   закладывается durable outbox с гарантированной досылкой.

## 1. Critical

### C-1 [архитектурно Critical / по текущему ущербу High] ERROR-ветка не гасит задачу → бесконечное перевыполнение (livelock)

**Файл:** `arena-bridge.ps1`, строки 178–202 (блок `catch`), в связке с
условием на строках 78–86 (`$taskId -ne $lastTaskId`).

**Суть.** Любое исключение в ветке выполнения (после того как `$lastTaskId`
ещё не обновлён) пишет результат `ERROR`, но **не** пишет `stateFile` и не
обновляет `$lastTaskId`. На следующем тике (через 1 секунду, строка 223)
та же задача выполняется **снова**. И так до бесконечности:

- `Push-Location $workDir` (строка 125) падает, если папка проекта
  переименована/удалена → вечный цикл `ERROR` каждую секунду, мост заклинен
  (новые задачи тоже не могут пройти — каждая падает так же);
- `gh` **отсутствует в PATH**: `& gh` бросает `CommandNotFoundException`
  (в `Send-ToGitHub` нет try/catch — исключение всплывает в `catch` моста,
  строка ~176) → команда уже выполнена, результат записан, state НЕ записан
  → **команда выполняется повторно каждую секунду**. Отдельно: обычный отказ
  API (сеть/401/422 при установленном `gh`) сюда НЕ приводит — `& gh`
  отрабатывает, `$LASTEXITCODE ≠ 0`, `Send-ToGitHub` делает 3 ретрая и
  возвращает `$false`; это H-2 (потеря результата), не C-1;
- запись result-файла не удалась (диск, права, на месте файла — каталог) →
  то же самое: повторное выполнение каждую секунду.

То есть C-1 — это одновременно нарушение exactly-once и полный клин моста
при персистентной причине. Текущий allowlist read-only, поэтому повторный
`git status` безвреден сам по себе, — но механизм replicate-then-fail уже
на месте, и любая будущая мутирующая команда в allowlist превратит его
в порчу данных. Плюс мост в этом состоянии спамит `ERROR` и не обслуживает
очередь.

**Repro** — см. R-1.

### C-2 [архитектурно Critical / по текущему ущербу High] Дедупликация однослотовая («не равен последнему») → replay тривиален

**Файл:** `arena-bridge.ps1`, строки 51–56 (чтение state), 78–86 (сравнение).

**Суть.** Мост помнит ровно один ID — последний. Любой ID, не равный
последнему, считается новым и выполняется:

- записать `007|git status` → выполнится;
- записать `008|git status` → выполнится;
- записать `007|git status` снова → **выполнится второй раз** (007 ≠ 008).

Чередованием двух ID одну команду можно выполнять бесконечно. Это не
дедупликация, а детектор «файл изменился». Монотонность не проверяется,
множество виденных ID не ведётся. Любой процесс, способный писать task-файл
(в т.ч. рассинхронизированный роутер, см. M-3, или ручная правка), получает
произвольные повторы.

**Repro** — см. R-2.

## 2. High

### H-1. Нет состояния RUNNING: сбой между выполнением и state → повтор после рестарта

**Файл:** `arena-bridge.ps1`, строки 125–171 (порядок: exec → result → state → publish).

Состояние задачи нигде не фиксируется как «выполняется». Окно между
выполнением команды (строки 128–133) и записью state (строки ~165–169):
`kill -9` / падение питания / Ctrl+C в этот момент → после рестарта мост
читает старый state → **команда выполняется второй раз**, затем публикуется
(дубликат комментария с тем же TASK ID). Зеркальное окно state→publish:
сбой после записи state, но до `Send-ToGitHub` → задача помечена готовой,
результат **никогда не доставлен и не будет** (нет outbox, см. H-2).

Это классический §2/§6 из ТЗ — подтверждено чтением кода. Repro — R-3
(через временную задержку в копии скрипта).

### H-2. Недоставка молча считается успехом: нет outbox, нет redelivery

**Файл:** `arena-bridge.ps1`, строки 25–49 (`Send-ToGitHub`), 175–176
(возвращаемое значение игнорируется: `Send-ToGitHub $resultText | Out-Null`).

Если все 3 попытки `gh api` провалились (нет сети, 401/403/422, даунтайм
GitHub), функция возвращает `$false`, мост это игнорирует — задача уже
помечена COMPLETED в state (state пишется **до** `Send-ToGitHub`, поэтому
повторного выполнения при отказе API НЕ происходит — теряется именно
результат). Результат остаётся только в локальном
result-файле (который затопчет следующая задача). После восстановления сети
**ничего не досылается**: офлайн-режима, очереди недоставленного и
reconnect-логики нет (§10 ТЗ — отсутствует целиком). Для системы, чья
единственная работа — доставка, молчаливая потеря результата — High.

Дополнительно: ретрай не идемпотентен — если первый POST фактически дошёл,
а ответ потерялся, повтор создаст **дубликат комментария** (API комментариев
идемпотентности не даёт, маркеров в теле для ручной сверки, кроме TASK ID,
нет). Repro — R-4.

### H-3. Нет проверки идентичности репозитория: команды бегут «где попало»

**Файл:** `arena-bridge.ps1`, строки 4 (`$workDir`), 125 (`Push-Location $workDir`).

Мост делает `Push-Location` в захардкоженный путь и выполняет `git status /
git diff / git log` без проверки, что это **тот самый** репозиторий. Если
папку подменили (другой клон, другой проект, junction/symlink, «восстановление»
OneDrive, переустановка машины) — мост опубликует в **публичный** Issue
`git status`/`git log` **чужого проекта**: имена файлов, веток, тексты
коммитов. Это прямой аналог урока с PLN-гардом из основного проекта:
«не сверил идентичность цели — не трогай». Repro — R-5.

### H-4. Роутер безусловно затирает task-файл → потеря невыполненной задачи

**Файл:** `arena-qwen-router.ps1`, строки 106–124.

Роутер вычисляет следующий ID из **state-файла** (последняя *выполненная*),
а не из task-файла (последняя *порученная*), и молча перезаписывает task-файл:

- сценарий А: роутер запустили дважды раньше, чем мост проснулся (тик 1 с) →
  вторая запись затирает первую; первая команда **потеряна навсегда**;
- сценарий Б: мост успел выполнить первую между двумя запусками, но второй
  запуск роутера прочитал state до обновления мостом → обе записи с одним ID,
  вторая команда **молча проигнорирована** мостом (ID равен последнему).

Роутер должен отказываться писать, пока в task-файле висит необработанный ID.
Repro — R-6.

## 3. Medium

### M-1. Рваное чтение task-файла → ложный BLOCKED съедает настоящую задачу

**Файл:** оба — писатель `arena-qwen-router.ps1:120–124` (`Set-Content`
напрямую), читатель `arena-bridge.ps1:63–74` (`Get-Content -Raw` в опросе).

Запись не атомарна (open/truncate/write/close), читатель опрашивает каждую
секунду. Мост может прочитать файл посередине записи: например, `004|git sta`
вместо `004|git status`. Дальше: формат валиден (ID + команда), команда не в
allowlist → **BLOCKED + state=004**. Настоящая задача 004 потеряна, в логе —
ложная блокировка обрезанной команды.

Важная good news (проверено): выполнить **чужую** команду рваное чтение не
может — ни одна команда allowlist не является префиксом другой, так что
усечение даёт только BLOCKED/IGNORED, но не подмену команды. Теряется
доступность, не целостность. Ответ на вопрос §3 ТЗ: **да, temp+rename нужен**
плюс толерантный читатель (повторное чтение / проверка стабильности файла).
Repro — R-7 (вероятностный).

### M-2. Неатомарная запись state → рваный state → повтор последней задачи

**Файл:** `arena-bridge.ps1`, строки ~110–115, ~165–169 (`Set-Content $stateFile`).

Убийство процесса посередине записи state даёт обрезанный ID (например, `00`
вместо `003`). После рестарта мост сравнит новый/старый ID с мусором → почти
наверняка выполнит задачу повторно (в связке с C-2). Лечится тем же temp+rename
и/или JSON-state с валидацией.

### M-3. Ненumeric ID рассинхронизирует счётчик роутера → переиспользование ID → повторы

**Файл:** `arena-qwen-router.ps1:106–118`, `arena-bridge.ps1:78–86`.

Мост принимает **любой** непустой ID, а роутер понимает только `^\d+$`.
Стоит один раз положить в task-файл ручную задачу (`abc|git status`, что
разрешено протоколом де-факто) — мост выполнит и запишет state=`abc`.
Следующий запуск роутера: `abc` не подходит под маску → fallback `lastId="000"` →
пишет `001|...` → мост видит 001 ≠ abc → **выполняет давно выполненный ID 001
повторно**. Протокол хрупок: формат ID не зафиксирован и не валидируется
одинаково с двух сторон. Repro — R-9.

### M-4. Нет таймаутов: зависший `gh`/`llama` вешает мост/роутер

- `arena-bridge.ps1:30–36` — `gh api` без таймаута, до 3 попыток. Сетевой
  stall вешает весь цикл моста (новые задачи не обрабатываются всё время
  висящих попыток).
- `arena-qwen-router.ps1:62–71` — `Invoke-RestMethod` без `-TimeoutSec`
  (дефолт 100 с). Зависший llama-server = зависший роутер на 100 с.

Нужны явные таймауты (gh — через обёртку с `timeout`/job + kill; роутер —
`-TimeoutSec 30`) и fail-closed выход.

### M-5. Неидемпотентная доставка: дубликаты комментариев

**Файл:** `arena-bridge.ps1:25–49`. Каждый повтор (H-1, C-1, C-2, ретрай после
фактически дошедшего POST) создаёт **новый** комментарий — API не даёт
клиентской идемпотентности, а мост не делает upsert. В теле есть TASK ID,
так что дубликаты видно глазом, но программно ChatGPT их не склеит.
Лечение: маркер `<!-- arena-task:007 -->` + поиск своего комментария
и PATCH-апдейт вместо нового POST (план в §9 отчёта).

### M-6. Публикация без лимита размера; `safeToPublish` требует ревизии

**Файл:** `arena-bridge.ps1:14–19`, тело `$resultText` (~строки 138–156).

- Нет обрезки результата: `git status` с тысячами untracked-файлов даст
  комментарий-гигант (лимит GitHub — 65536 символов, дальше 422 → см. H-2).
- Публикуются имена файлов, ветки, **тексты коммитов** (`git log`). Тексты
  коммитов — неконтролируемый ввод: туда попадают тикеты, имена, иногда
  секреты/URL. Решение `git diff` не публиковать — правильное (отмечаю как
  верное), но для `log`/`status` нужны: лимит длины + пометка `[truncated]`
  + явное решение «коммиты можно светить» (или редизайн: публиковать только
  `git status --short --branch` и хеши без сообщений).
- Прямых секретов (токены, пароли, env) в публикуемом теле **нет** — проверено:
  ERROR/BLOCKED не публикуются вообще (а именно в exception-текстах живут
  абсолютные пути), env в тело не входит. По §5: `safeToPublish` достаточен
  против секретов, недостаточен против спама/метаданных.

### M-7. Нет персистентного аудит-лога; BLOCKED/ERROR не видны ChatGPT

Оба скрипта только `Write-Host` в консоль (§11 ТЗ отсутствует). После
перезапуска/потери консоли истории нет: что просили, что решили, какой exit
code, что опубликовали (comment id?) — восстановить нельзя. Отдельно:
ветки BLOCKED (мост) и exit 2/3 (роутер) **никому не сообщаются** —
ChatGPT ждёт результата, которого не будет, и не знает почему. Нужны:
append-only JSONL-лог (без секретов) + публикация статусных маркеров
BLOCKED/ERROR без чувствительного содержимого.

### M-8. Task-файл — неаутентифицированный триггер публичного раскрытия

Любой процесс от имени пользователя (вредонос, чужой скрипт, второй оператор),
способный записать `003|git log --oneline -10` в task-файл, автоматически
получает публикацию состояния репозитория в публичный Issue — мост не
различает «задачу от роутера» и «задачу от кого угодно». По §1 ТЗ «подмена
task-файла»: инъекции нет (allowlist держит), но есть **несанкционированный
запуск + disclosure**. Repro — R-12. Лечение — подписанные задачи в целевой
архитектуре (§8 отчёта); быстрое — подтверждение публикации для `log`.

### M-9. Два запущенных моста → двойное выполнение + рваный state (нет мьютекса)

Нигде нет single-instance защиты. Два процесса `arena-bridge.ps1` (двойной
клик, перезапуск забывчивым оператором) опрашивают одни файлы: оба увидят
задачу, оба выполнят, оба опубликуют, записи result/state перемежаются.
Repro — R-11. Лечение: именованный мьютекс (`Global\ArenaBridge`) с
fail-closed выходом второго экземпляра.

### M-10. Баг форматирования: многострочный вывод схлопывается в одну строку

**Файл:** `arena-bridge.ps1:128–133` + интерполяция `"$result"` в here-string.

`$result` — массив строк; в here-string массив раскрывается через `$OFS`
(пробел). `git log --oneline -10` в result-файле **и** в опубликованном
комментарии выглядит как одна длинная строка. Детерминированный баг,
repro — R-8. Лечение: `($result -join "`r`n")` / `Out-String`.

### M-11. Публичный Issue — спуфинг результатов никем не отличим

Комментарии в Issue #1 может оставлять кто угодно. Злоумышленник (или шутник)
постит поддельный `[LOCAL RESULT 005] ...` — ChatGPT, читающий Issue как
почтовый ящик, не отличит подделку от настоящего (формат маркера публичен,
подписи нет). Быстрое лечение: ChatGPT обязан проверять `author == владелец
репо` у каждого комментария-результата; правильное — подпись/маркер апдейта
в целевой архитектуре.

### M-12. Папка Documents может синкаться в OneDrive → утечка + рваные чтения

Пути захардкожены в `$env:USERPROFILE\Documents` (оба файла, строки 1–4).
Если на машине включён OneDrive Backup — task/result-файлы (включая локальный
`git diff`, который специально не публикуется!) уезжают в облако, а
конфликты синхронизации добавляют рваных чтений сверх M-1. Лечение: переезд
на `%LOCALAPPDATA%\ArenaBridge` (не синкается) + проверка при старте.

## 4. Low

- **L-1. Case-insensitive allowlist.** `-in`/`-notin` регистронезависимы:
  `GIT STATUS` проходит allowlist, затем падает в git (`'STATUS' is not
  a git command`) и публикуется как COMPLETED с exit 1. Инъекции нет
  (доказано: case-фолдинг не порождает метасимволы, а отличающиеся буквы
  роняют git), но семантика «COMPLETED» врёт. Repro — R-10. Лечение: `-cin`
  + канонизация команды перед выполнением.
- **L-2. COMPLETED при ненулевом exit.** Статус не зависит от кода возврата
  (мост, ~строки 138–156). Код в теле есть, так что видно, но статус должен
  быть FAILED при exit ≠ 0.
- **L-3. Спам `IGNORED` + тихий игнор.** Task-файл без `|` — `Write-Host
  IGNORED` **каждую секунду**; пустой ID (`|git status`) — наоборот, тихое
  ничего. Нужны троттлинг лога и явное сообщение во втором случае.
- **L-4. Схема ответа Qwen не валидируется.** Роутер, строка 85:
  `$response.choices[0].message.content.Trim()` — при `choices: []` падает
  с необработанным исключением (fail-closed, задача не пишется — это хорошо,
  но выход уродливый и код тот же 1, что у «нет файла»). Нужна явная проверка
  и отдельный exit code.
- **L-5. Symlink/junction на task/result/state.** Сейчас тот же пользователь —
  риск минимален; но мост **пишет** по этим путям, и если мост когда-нибудь
  запустят elevated — symlink = произвольная запись. Дешёвое лечение: при
  старте проверять `ReparsePoint` и падать fail-closed.
- **L-6. Нет лимита размера task-файла.** `Get-Content -Raw` грузит всё
  в память; локальный дебош (гигабайтный файл) = дебош моста. Лимит 4–64 КБ.
- **L-7. Ретрай жжёт rate-limit.** Фиксированные 2 с, без разбора 403/429
  и `Retry-After`. Экспоненциальный backoff + стоп на 401/404/422.
- **L-8. Result-файл хранит только последнее.** Перезапись, не append —
  предыдущий результат (включая неопубликованный `git diff`) испаряется.
  Хотя бы ротация `result-<id>.txt`.
- **L-9. Дублирование allowlist в двух файлах.** Изменение в одном без
  другого = рассинхрон (мёртвая команда или дыра в UX-фильтре). Один общий
  файл/конфиг, подключаемый обоими.
- **L-10. COMPLETED публикуется, даже если git ругнулся на не-репо.**
  Следствие H-3 + L-2: `fatal: not a git repository` уедет в публичный Issue
  как «успех». Лечится H-3 и L-2 вместе.

## 7. Repro steps (конкретные, для машины пользователя)

Соглашения: `$D = "$env:USERPROFILE\Documents"`, мост запущен в отдельном
окне. **Осторожно:** R-1/R-2/R-5/R-9/R-11 плодят выполнения и комментарии —
делать на тестовом Issue или быть готовым чистить Issue #1.

**R-1 (B-1: вечный ERROR / ре-exec).** Вариант А (клин без выполнения):
переименовать папку проекта → в task-файл `900|git status` → наблюдать
`ERROR` каждую секунду бесконечно; вернуть папку → мост сам подхватит.
Вариант Б (ре-exec после успеха): остановить мост; удалить result-файл;
создать **каталог** с именем result-файла → запустить мост →
`900|git status` → команда выполняется, запись результата падает → ERROR →
через секунду команда выполняется **снова** (видно по логу/счётчику).
Убрать каталог-призрак после проверки.

**R-2 (B-2: replay).** По очереди с паузой >1 с записать в task-файл:
`901|git --version`, затем `902|git --version`, затем снова
`901|git --version` → третья запись **выполнится** (в логе `NEW [901]`,
в Issue — второй комментарий с TASK ID 901).

**R-3 (H-1/B-10: окно exec→state).** Сделать **копию** моста для теста,
вставить `Start-Sleep 10` между выполнением и записью state; отправить задачу;
во время сна убить процесс (`Stop-Process -Force`); запустить мост заново →
задача выполнится **второй раз**. (Без правки кода окно — миллисекунды,
ловится только код-ревью; механика та же.)

**R-4 (B-3: потеря доставки).** Временно сломать auth: `$env:GH_TOKEN='bad'`
в окне моста → задача → `GitHub send failed ×3` → COMPLETED локально,
комментария нет → вернуть токен → **досылки нет**, результат потерян для
ChatGPT (лежит только в result-файле до следующей задачи).

**R-5 (H-3: чужой репо).** Переименовать проект, на его месте `git init` +
коммит с маркером → `git log --oneline -10` → в публичном Issue появится лог
**подставного** репозитория. Вернуть всё назад.

**R-6 (B-4: затирание).** Остановить мост. Дважды подряд (разные просьбы)
запустить роутер → в task-файле только вторая задача; запустить мост →
выполнится только она, первая потеряна без следа.

**R-7 (B-7: рваное чтение).** Цикл-писатель в фоне каждые 50 мс пишет
`910|git log --oneline -10` через `Set-Content`; мост работает; повторять,
пока в логе не появится `BLOCKED [910]: git log --oneline -1` (или иной
обрезок) — задача съедена ложной блокировкой. (Вероятностный; на быстром
диске может потребовать много итераций.)

**R-8 (B-5: схлопывание).** `911|git log --oneline -10` → открыть result-файл:
все коммиты одной строкой через пробелы. То же — в комментарии GitHub.

**R-9 (B-8: сброс счётчика).** Вручную `abc|git --version` → мост выполнит,
state=`abc` → запустить роутер с любой просьбой → он запишет `001|...` →
мост выполнит ID 001 (возможно, давно выполненный) повторно.

**R-10 (B-6: регистр).** `912|GIT STATUS` → проходит allowlist → git падает →
публикуется COMPLETED с exit 1 и текстом `'STATUS' is not a git command`.

**R-11 (B-9: двойной мост).** Запустить два окна моста → одна задача →
два выполнения + два комментария + перемежающиеся записи state.

**R-12 (M-8: чужой триггер).** Любым способом (другой пользовательский процесс,
планировщик, ручная правка) записать валидную строку в task-файл → мост
выполнит и опубликует без единого вопроса.

## 8. Целевая архитектура

### 8.1. Принципы (не меняются со следующего этапа)

1. Qwen недоверенна всегда; GitHub Issue публичен всегда.
2. Модель выбирает **action_id из таблицы**, never — текст команды.
   Выполнения «строки через -Command» не существует как класса.
3. Каждая задача — подписанный конверт с монотонным seq (см. 8.3),
   replay технически невозможен, а не «маловероятен».
4. Состояния персистентны (8.2); доставка — через outbox с upsert (8.4).
5. Всё пишется в append-only аудит-лог; секретов в логах/Issue нет.

### 8.2. State machine (закрывает §6 ТЗ)

Состояния задачи: `NEW → VALIDATED → RUNNING → COMPLETED → PUBLISHED`,
боковые: `BLOCKED`, `FAILED`. Хранение: один JSON-файл состояния
(атомарно через temp+rename) вида:

```json
{
  "seq": 12,
  "tasks": {
    "012": {"state": "PUBLISHED", "action": "git_status", "exit": 0,
            "result_sha256": "…", "comment_id": 3456789012,
            "updated": "2026-09-22T12:00:00"}
  }
}
```

Правила переходов:

- `NEW→VALIDATED`: подпись сошлась + seq = last_seq+1 + action_id известен.
  Иначе — `BLOCKED` (подпись/формат) — и точка, без выполнения.
- `VALIDATED→RUNNING`: ставится fence `{pid, started}`; исполнитель один
  (мьютекс); crash в RUNNING при старте → `FAILED(recovered)` с записью в лог
  (политика «не повторять вслепую»; повтор только руками с новым seq).
- `RUNNING→COMPLETED`: exit зафиксирован; exit≠0 → `COMPLETED(exit≠0)` всё
  равно идёт в outbox, но со статусом FAILED — ChatGPT видит и то, и другое.
- `COMPLETED→PUBLISHED`: только после HTTP 201 от GitHub + сохранённого
  `comment_id`. Недоставленное лежит в outbox вечно (до TTL/ручной чистки),
  publisher жужжит по таймеру и досылает (закрывает H-2, офлайн, reconnect).
- Дедуп: `seq ≤ last_seq` → игнор как дубликат (протокол монотонный —
  закрывает C-2 и M-3 целым классом).

### 8.3. Подписанные задачи (обратный канал, закрывает §12 ТЗ)

Сравнение вариантов из ТЗ:

| Вариант | NAT/фаервол | Секретность | Сложность | Вердикт |
|---|---|---|---|---|
| Polling публичного Issue | работает везде | нет (всё видно) | низкая | только для чтения чужих задач — не подходит как есть |
| Отдельный **приватный** mailbox-репо | работает везде | да (читают только с токеном) | низкая | **рекомендую как транспорт** |
| Локальный HTTP relay (127.0.0.1 + токен) | нужен туннель наружу | да | средняя | этап C, для push-интеграций |
| WebSocket наружу | нужен сервер/туннель | да (TLS) | средняя-высокая | избыточен, пока хватает polling |
| GitHub Actions как исполнитель | — | — | — | не подходит: Actions не имеет доступа к локальной машине |

Рекомендация: **приватный mailbox-репо + подписанные конверты + polling**:

- ChatGPT (через пользователя/автоматизацию с токеном) кладёт задачу как
  Issue/файл в приватном репо; мост опрашивает его раз в N секунд.
- Конверт: `{seq, nonce, ts, action_id, args_hash, hmac}` —
  HMAC-SHA256 по каноническому JSON, секрет в Credential Manager (DPAPI),
  никогда в файлах/Issue. Проверка: HMAC + `seq = last+1` + `|now-ts| < 10 мин`
  + nonce не виден ранее (окно последних 1000). Это закрывает M-8/M-11/C-2
  одним механизмом: чужой/повторный/просроченный конверт не выполняется.
- Результат публикуется туда же (приватно) upsert-ом по маркеру
  `<!-- arena-task:{seq} -->`: свой комментарий ищется и PATCH-ится —
  дубликатов нет даже при ретраях (закрывает M-5). Публичный Issue #1
  остаётся только для явно разрешённых safe-выводов — по одному флагу
  `publish_public: true` в политике действия.
- Проверка автора (`author == owner`) остаётся дешёвым вторым рубежом.

### 8.4. Исполнитель без shell-строк (закрывает §9 ТЗ)

Таблица `action_id → ScriptBlock` с типизированными аргументами и политикой:

- `git_status`, `git_log10`, `git_version` — read-only, автозапуск;
  запуск напрямую: `& git -C $workDir status --short --branch`
  (никаких `powershell -Command "<строка>"`, никакого cwd-жонглирования
  через Push/Pop в общем процессе);
- `git_diff` — read-only, но `publish_public: false` всегда (наследует
  сегодняшнее верное решение);
- будущие мутирующие действия — только с `approval: interactive` (файл
  подтверждения/клик) и с явным флагом «разрешён повтор — да/нет»
  (идемпотентные — да, остальные — только руками).
- Перед каждым запуском — guard идентичности репо:
  `git -C $workDir remote get-url origin` == ожидаемому **и**
  `rev-parse --show-toplevel` резолвится внутрь ожидаемого пути
  (никаких symlink-побегов) — иначе fail-closed (закрывает H-3, L-5).

### 8.5. Файлы и процессы

- Все рабочие файлы — в `%LOCALAPPDATA%\ArenaBridge` (не синкается, см. M-12);
  записи — temp+rename; читатель проверяет стабильность (размер/mtime
  не менялись 200 мс) перед разбором.
- Single-instance: именованный мьютекс, второй экземпляр умирает с кодом 5.
- Аудит-лог: `audit-YYYY-MM-DD.jsonl`, append-only, строка =
  `{ts, seq, action, exit, result_sha256, comment_id, error_class}` —
  без тел выводов и секретов (§11 ТЗ). Отдельно — ротация result-файлов
  `result-<seq>.txt` (L-8).
- Роутер остаётся «советчиком», не «привратником»: он готовит **проект
  конверта**, а подписывает его отдельная локальная роль (тот же пользователь,
  но другой шаг/подтверждение) — тогда скомпрометированная Qwen не может
  сама себе выписать подписанную задачу.

## 9. Patch plan (по приоритетам, код не трогаю — только план)

**P0 — exactly-once (C-1, C-2, H-1). Без этого всё остальное косметика:**

1. `bridge`: в `catch` (ERROR-ветка) — гасить задачу: писать state + статус
   `FAILED` в result, вводить счётчик попыток и backoff; вечный цикл запретить.
2. `bridge`: монотонный `seq` вместо «≠ последнему»: numeric ID, `seq ≤ last →
   дубликат, игнор`; ручные ненumeric ID — в BLOCKED, не в выполнение.
3. `bridge`: персистентный RUNNING-fence (pid+время) + recovery при старте
   (RUNNING → FAILED-recovered, без автоповтора).
4. `router`: не писать поверх необработанного task (сверка task vs state),
   единый numeric seq из одного счётчика.

**P1 — доставка и целостность (H-2, H-3, M-5, M-11, M-8):**

5. Outbox недоставленного + publisher по таймеру + upsert комментария
   по маркеру `<!-- arena-task:N -->` (идемпотентность, reconnect, дубликаты).
6. Guard идентичности репо (remote URL + realpath) перед каждым запуском,
   fail-closed.
7. Публикация статусных маркеров BLOCKED/FAILED (без чувствительного тела),
   чтобы ChatGPT не ждал молча.
8. ChatGPT: сверять `author` комментариев-результатов с владельцем репо
   (временная мера против спуфинга до подписей).

**P2 — транспорт файлов и процессы (M-1, M-2, M-4, M-9, M-12, L-5, L-9):**

9. Temp+rename для task/result/state + толерантный читатель.
10. Именованный мьютекс single-instance.
11. Таймауты: `-TimeoutSec` роутеру, обёртка с таймаутом для `gh`.
12. Переезд из Documents в `%LOCALAPPDATA%`; проверка ReparsePoint при старте.
13. Единый allowlist-файл, подключаемый обоими скриптами.

**P3 — гигиена вывода и логов (M-6, M-7, M-10, L-1–L-4, L-6–L-8, L-10):**

14. `-join "`r`n"` для `$result`; `-cin` + канонизация команды; FAILED при exit≠0.
15. Лимит размера результата + `[truncated]`; ревизия `safeToPublish` для `log`.
16. Append-only JSONL аудит-лог; ротация `result-<seq>.txt`; троттлинг IGNORED;
    валидация схемы ответа Qwen с отдельным exit code; лимит размера task-файла.

**Следующий этап (по §8 отчёта):** приватный mailbox-репо → подписанные
конверты (HMAC+seq+nonce+ts) → action-таблица вместо строк → approval для
мутаций → локальный HTTP relay опционально.
