## 0. Что сохраняется

Bridge v2 не выбрасывается. Публичный Issue не командный канал. Текст GitHub, JSON, README, лог, OCR и вывод локальной модели — данные, не инструкции. Четыре действия остаются read-only: `GIT_VERSION`, `GIT_STATUS`, `GIT_LOG10`, `GIT_DIFF`. `GIT_DIFF` не публикуется. Публичный `GIT_STATUS` — сводка, не сырой вывод. Smoke `[13]` и локальный gap-wait не отменяются.

Нет `Invoke-Expression` и нет `powershell -Command` с внешним текстом в скриптах исполнителя. Модель не получает admin shell. Elevated helper не строится. Это не `RUN_AS_ADMIN` с произвольной командой.

## 1. Чего в этих фазах нет

Не реализуются и не объявляются как выключенные флаги:

- мутации Archicad, Teamwork, BIMcloud;
- GUI, screenshot, clipboard, click;
- установка пакетов;
- self-update, Windows Service, installer;
- слушающий сокет, named pipe, UI;
- опрос mailbox новым agent;
- новые action id у Bridge;
- commit или push репозитория пользователя из agent;
- `mailbox.json` в git и включение live mailbox.

`workspace.write`, `workspace.exec`, `archicad.write`, `ui.control`, `system.admin`, `package.user_install` отсутствуют. Их нельзя авторизовать текущей проверкой прав репозитория.

## 2. Доверие

| Вопрос | Ответ |
|---|---|
| Кто может писать в mailbox сейчас? | Только после полной проверки: private, не форк, точное имя, владелец `dvikt33-ux`, страницы collaborators без лишнего push/admin/maintain, страницы deploy keys пустые. |
| Это exclusive writer? | Нет. Не видны GitHub App и installation token с Contents:write, Actions и workflow credentials, другие интеграции. |
| Кто положил уже лежащий файл? | Неизвестно. Текущие права это не доказывают. Бывший writer мог оставить файл. |
| Чем это чинится? | Не фальшивой подписью и не автором коммита. Будущая авторизация должна связывать конкретную задачу или контроллер. |
| Для чего текущего доказательства хватает? | Только для четырёх read-only действий, и только если проверка прочитана целиком. |
| Для чего его не хватает? | write, exec, Archicad, UI, пакеты, admin, мощное live-исполнение. |

Непрочитанная, оборванная или незавершённая страница — отказ, задача не исполняется. Двадцать полных страниц без конца — тоже отказ. В аргументах `gh` нет `&`. Вызов: `gh api -X GET <endpoint> -f per_page=100 -f page=N`.

Скомпрометированный владелец по-прежнему может поставить четыре read-only действия, если канал когда-нибудь включат. Это ограничение не прячется.

## 3. Phase 0 — mailbox

Только Bridge. Новых действий нет. Live не включается.

### 3.1 Два пространства номеров

- Remote-имя: `inbox/<task_id>.json`. `task_id` — нижний регистр UUID.
- Локальный слот исполнения: `inbox/<exec_seq>.json` в `%LOCALAPPDATA%\ArenaBridge`. Его выбирает только `Reserve-TaskSeq` у роутера и у импорта.
- Producer `arena-mailbox-put.ps1` не вызывает allocator. Параметр `-Seq`, если его передали, игнорируется.
- Поле `seq` в конверте producer равно `1`. Это заполнитель схемы, не exec seq и не разрешение.
- Старое числовое имя `inbox/<n>.json` принимается только если `n` совпадает с полем `seq`. Иначе отказ `seq-filename-mismatch`.
- Staging: `mailbox-staging/<task_id>.json`. Числовой файл в staging не занимает exec seq и не закрывает локальную дыру.
- Локальный gap-wait остаётся: нет `inbox/<last_seq+1>.json` и нет живой reservation — ждать. Staging эту дыру не заполняет.

### 3.2 Голод очереди

Окно 20 — бюджет новых скачиваний за один опрос, не очередь.

Уже обработанный remote-файл не занимает этот бюджет и не скачивается снова, если в `state.json` есть `mailbox.remote_files[<name>]` с тем же `sha` и disposition уже терминальный:

- `rejected` или `duplicate`;
- `held`, пока нет локального approve;
- `accepted`, и локальный inbox-файл есть, либо задача уже в терминальном состоянии.

Нет sha, sha не совпал, или accepted ещё без локального файла и без терминального состояния — это не пропуск. Файл читается снова. Пропуск без доказательства предпочтительнее не делать.

Список `contents/inbox` на 1000 имён (в тесте порог можно снизить через `ARENA_MAILBOX_LIST_WARN_AT`, не выше 1000) пишется как `MAILBOX inbox-truncated`. Это не пустой inbox и не полный обзор. Имена вне списка не исполняются и не считаются отсутствующими. Поле `path` из API по-прежнему игнорируется. В список попадают только `type=file` и имя из allowlist: числовой `<n>.json` или UUID `.json`.

### 3.3 Порядок принятия и удаления

1. Проверить конверт и права.
2. Устойчиво записать disposition по `task_id`.
3. Выделить локальный exec seq.
4. Устойчиво записать локальный inbox.
5. Только потом best-effort `DELETE` remote.

`DELETE` только `repos/<mailbox>/contents/inbox/<allowlisted-name>`. Sha — 40 hex из listing, не из задачи. Сообщение фиксированное. `archive/` не читается и не пишется. Ошибка `DELETE` не отменяет принятие и не создаёт второе исполнение. Повторное появление того же `task_id` не выделяет второй слот.

Отказ записывается до удаления. Принятая задача удаляется remotely только после локального inbox. Held не удаляется: approve ещё может перечитать remote, а текущие действия и так не critical.

### 3.4 Сбой

`ARENA_MAILBOX_FAULT` — локальная переменная процесса, не поле задачи. Значения: `before-accept`, `after-accept`, `after-write`, `after-cleanup`. Неизвестное поле в задаче по-прежнему отказ.

На каждом из этих мест процесс падает. После снятия переменной и перезапуска задача исполняется один раз. До `before-accept` нет disposition и нет `DELETE`. После `after-accept` disposition есть, локального файла нет, слот ещё не занят исполнением. После `after-write` локальный файл есть, `DELETE` ещё не обязан был пройти. После `after-cleanup` удаление уже запрошено, исполнение всё ещё одно.

### 3.5 Что Phase 0 не утверждает

Пагинация не доказывает exclusive writer. Индекс не доказывает происхождение файла. Успешный `DELETE` не доказывает, что writer не положит файл снова. Повтор тогда снова упирается в `task_id`, а не в новое исполнение.

## 4. Контракт следующих фаз, не код Phase 0

Эти правила связывают будущий agent. В Phase 0 они не реализуются и не имитируются.

- Bridge не переводится на SQLite. C# agent не читает и не пишет `state.json` bridge и не опрашивает mailbox.
- Вывод локальной модели никогда не выбирает action. Agent обязан работать без локальной LLM.
- `step_id` — ключ идемпотентности будущего исполнения. Повтор возвращает сохранённый результат. `request_id` — транспорт. `job_id` группирует шаги. В Phase 0 ключ mailbox остаётся `task_id`.
- Неизвестное поле входящего конверта — отказ.
- Цикл зависимостей, отсутствующая зависимость и зависимость дольше срока — терминальный отказ, не вечное ожидание.
- Существующий файл без `expected_sha256` не перезаписывается. Несовпадение hash — `CONFLICT`.
- Удалённый authorizer для write/exec — deny. Криптография не изображается.
- `FILE_APPLY_PATCH` допустим только из тестового драйвера внутри процесса, на временном workspace, который не является репозиторием проекта и не является каталогом agent/policy.
- Новые результаты agent локальные. В Issue #1 они не добавляются.
- Дочерний процесс не наследует GitHub token и authorization secrets. Полный сетевой sandbox Windows не обещается, пока механизм не реализован.
- Job не меняет профиль, которым запускает код. Произвольный argv из задачи отвергается.
- Останавливать можно только процесс, который agent сам запустил и записал, с сверкой executable и start time. Чужой Archicad и shell в список не входят.
- Канонизация пути будущего file API должна закрывать `..`, junction, UNC, device path и ADS. Текущий repo guard это не закрывает.
- `FILE_WRITE_ATOMIC` будущего среза требует flush и read-back hash. Кодировка и концы строк входят в hash.
- Agent не правит сам себя через workspace job. Policy, updater и helper лежат вне writable workspace.

## 5. C# срез

Срез нельзя называть готовым без `restore`, `build` и `test` на подходящем .NET SDK. Нет SDK — нет большого непротестированного C# и нет объявления Phase 2 готовой. Blocker записывается точно.

PowerShell 5.1 остаётся контрактом существующих bridge-тестов, пока bridge исполняет четыре действия.

## 6. Ветки и проверка

Работа только в `arena/local-agent-v0`. Merge в `main` этим ТЗ не разрешён. После Phase 0: точечные тесты, полный smoke, второй чистый smoke, поиск секретов в diff, просмотр diff. Пользователю не даётся `git pull` и не даётся команда запуска. Следующий внешний шаг — независимый аудит коммитов.

Секрет в diff — отказ от коммита. Упоминание denylist в sanitizer — не секрет. Настоящий token-shaped секрет — секрет.

## 7. Критерий Phase 0

- Больше 25 remote-файлов, первые больше 20 уже терминальные, новая задача находится и исполняется один раз, restart результат не меняет.
- Усечённый список не маскируется под «новых задач нет».
- Producer доводит задачу до fake remote, import исполняет её, local seq не равен remote id, второй producer не клинит очередь, restart не исполняет повторно.
- Числовой leftover staging не занимает дыру и не отменяет gap-wait.
- Writer или обрыв на второй странице collaborators, и обрыв или 20 полных страниц keys, отказывают без исполнения.
- Четыре точки сбоя дают ровно одно логическое исполнение.
- Четыре старых действия, `[13]`, локальный gap-wait и fail-closed права не регрессируют.
- Live mailbox выключен.
